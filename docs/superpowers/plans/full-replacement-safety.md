# 数据库全量覆盖：待实施安全方案

目标是先准备完整结果，再替换目标；恢复和提交状态必须可判断。以下是实施约束，不代表功能已上线。

1. 为目标数据库预先创建专用暂存表、目标锁表和提交凭证表；暂存记录使用不可猜测的执行实例批次标识，验证暂存表与目标表属于同一可事务数据库且不是同一物理对象。
2. 完整读取源并写入当前批次暂存，校验字段映射和行数后提交准备事务。源目标为同一物理表时，必须在替换前完成读取。源读取或暂存失败时不得修改目标。
3. 在目标数据库获取目标表的规范化物理标识对应的锁；平台对该目标表的追加、更新和覆盖均需遵守同一锁。锁粒度不能仅依赖平台数据源编号，因为多个配置可能指向同一张表。
4. 对初版支持的数据库确认目标和暂存表具有可靠的事务语义；无法检查时拒绝。存在触发器、入站或出站外键且副作用无法确认时拒绝。目标表的外部写入也必须受同一隔离方案约束，否则不得宣称独占或原子切换。
5. 在单个目标事务中执行参数化批次筛选的 `DELETE` + `INSERT ... SELECT`，同时写入执行批次提交凭证；禁止使用导致隐式提交的 `TRUNCATE`、运行时 DDL 或重命名。失败必须回滚，不支持的目标直接拒绝。
6. 连接中断或进程故障时，重新连接目标数据库读取同事务写入的凭证，区分已提交和未提交。无法核验时标记未知，禁止自动重试及清理恢复证据。暂存清理由可追踪的独立流程处理。
7. 默认拒绝空结果覆盖，需明确启用；按日期补跑禁止全表覆盖。平台重试和恢复不得在未确认目标提交状态时盲目重放。
8. 先为 MySQL 8 InnoDB 构建故障、同库同表、并发、空结果和回滚集成测试，再分别验证 PostgreSQL 和 Oracle；未完成对应数据库验证前，不能声明支持该数据库的覆盖功能。
